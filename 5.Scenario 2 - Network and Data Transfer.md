# CSP → EA Tenant Migration: Network & Data Transfer Guide

This document covers the end-to-end network setup and data transfer strategies required when migrating workloads and data from an Azure CSP tenant to an Azure EA tenant (different Entra ID directories). It is intended to be used alongside the network architecture migration steps in [4.Scenario 2 - Network considerations.md](4.Scenario%202%20-%20Network%20considerations.md).

---

## Overview

Since Azure does not support direct resource moves across tenants, all data must be **actively transferred** from the CSP source subscription to the EA target subscription. The network architecture you put in place during migration directly determines:

- Transfer **speed** (bandwidth between tenants)
- Transfer **cost** (egress charges)
- Transfer **security** (encryption in transit, private vs. public endpoints)
- Transfer **reliability** (resumability, checksums, error handling)

---

## Part 1 — Network Connectivity Options for Data Transfer

Choose the connectivity model that matches your security, speed, and cost requirements. Multiple options can be combined.

### Option A — Internet (Public Endpoints) — Simplest

```
CSP Tenant                          EA Tenant
┌──────────────────────┐            ┌──────────────────────┐
│  Source Storage /    │  HTTPS/TLS │  Target Storage /    │
│  Databases           │ ─────────► │  Databases           │
│  (Public Endpoint)   │  Internet  │  (Public Endpoint)   │
└──────────────────────┘            └──────────────────────┘
```

**When to use:**
- Non-sensitive data
- Small-to-medium datasets (< 1 TB)
- No existing cross-tenant private connectivity

**Security requirements:**
- Enable storage firewall rules — restrict to specific IP ranges
- Use SAS tokens with minimum permissions and short expiry (< 1 hour)
- Enable TLS 1.2 minimum on all endpoints
- Disable public access after migration completes

**Cost:**
- CSP tenant egress charges apply (~$0.05–$0.08/GB depending on region)
- No ingress cost on EA side

---

### Option B — VNet Peering + VPN Gateway (Cross-Tenant Private)

```
CSP Tenant                                    EA Tenant
┌─────────────────────┐                      ┌─────────────────────┐
│  VNet (CSP)         │  S2S VPN Tunnel       │  VNet (EA)          │
│  10.0.0.0/16        │ ◄──────────────────► │  10.1.0.0/16        │
│                     │  Encrypted tunnel     │                     │
│  Source resources   │  (IKEv2, AES-256)    │  Target resources   │
└─────────────────────┘                      └─────────────────────┘
```

**When to use:**
- Large datasets (> 1 TB)
- Sensitive / regulated data requiring private transfer
- Long-running migration with ongoing replication

**Setup steps:**
1. Deploy VPN Gateway in each tenant's VNet (see [4.Scenario 2 - Network considerations.md](4.Scenario%202%20-%20Network%20considerations.md) Phase 3, Step 7–8)
2. Exchange public IPs and pre-shared keys between teams
3. Create Site-to-Site VPN connections in both tenants
4. Validate tunnel status: `az network vpn-connection show --query connectionStatus`
5. Route transfer traffic through the VPN by using private IPs / private endpoints

**Throughput:**
- VpnGw1: ~650 Mbps aggregate
- VpnGw2: ~1 Gbps aggregate
- VpnGw3: ~1.25 Gbps aggregate

**Cost:**
- VPN Gateway hourly charge (~$0.19–$0.40/hr depending on SKU)
- Cross-tenant VPN data transfer: standard egress rates apply
- Cheaper than Internet egress for large sustained transfers

---

### Option C — ExpressRoute (Highest Performance, Private)

```
CSP Tenant                On-Premises / ExpressRoute          EA Tenant
┌──────────────┐          ┌─────────────────────────┐        ┌──────────────┐
│  VNet (CSP)  │ ER Circ  │   ER Meet-Me Location   │ ER Auth│  VNet (EA)   │
│              │ ────────►│   (Private Peering)      │───────►│              │
└──────────────┘          └─────────────────────────┘        └──────────────┘
```

**When to use:**
- Very large datasets (> 10 TB)
- Regulatory requirements for dedicated private circuit
- Existing ExpressRoute circuit with available bandwidth

**Key considerations:**
- Requires re-authorization of the ExpressRoute circuit in the EA tenant (see Section 5 of [4.Scenario 2 - Network considerations.md](4.Scenario%202%20-%20Network%20considerations.md))
- If the circuit is CSP-owned, a new customer-owned circuit must be provisioned in the EA subscription
- Throughput scales with circuit bandwidth (1 Gbps, 2 Gbps, 5 Gbps, 10 Gbps)

**Cost:**
- Circuit monthly fee + data metered/unlimited plan
- No egress charges for data transferred over ExpressRoute (metered plan: per-GB charge)

---

### Option D — Azure Data Box (Offline Physical Transfer)

**When to use:**
- Datasets > 40 TB where network transfer would take weeks
- Limited network bandwidth available
- One-time bulk migration (not ongoing replication)

| Device | Usable Capacity | Use Case |
|---|---|---|
| Data Box Disk | 35 TB | Small bulk transfers |
| Data Box | 80 TB | Medium bulk transfers |
| Data Box Heavy | 770 TB | Large bulk transfers |

**Process:**
1. Order Data Box from the **EA target subscription** (Azure portal → Data Box)
2. Ship device receives data from CSP source on-premises or in a datacenter
3. Microsoft ships data to the EA subscription's storage account
4. Data is encrypted with AES-256 at rest on the device

## Part 2 — Data Transfer Tools by Service Type

### 2.1 Azure Blob Storage / ADLS Gen2

**Recommended tool: AzCopy**

AzCopy is the primary tool for cross-tenant blob storage migration. It supports direct service-to-service copy without staging data locally.

**Prerequisites:**
- AzCopy v10+
- Source: Storage Account with SAS token (Reader + List + Read on blobs)
- Destination: Storage Account with SAS token (Writer + Create + Write on blobs)
- Or use Entra ID (Azure AD) authentication with `--login` if the migration account exists in both tenants

**Copy an entire container:**
```bash
azcopy copy \
  "https://<source-storage>.blob.core.windows.net/<container>?<source-SAS>" \
  "https://<target-storage>.blob.core.windows.net/<container>?<target-SAS>" \
  --recursive=true \
  --log-level=INFO \
  --check-md5=FailIfDifferent
```

**Copy specific folder/prefix:**
```bash
azcopy copy \
  "https://<source-storage>.blob.core.windows.net/<container>/<folder>?<source-SAS>" \
  "https://<target-storage>.blob.core.windows.net/<container>/<folder>?<target-SAS>" \
  --recursive=true
```

**Resume an interrupted transfer:**
```bash
azcopy jobs resume <job-id>
```

**Check transfer status:**
```bash
azcopy jobs list
azcopy jobs show <job-id>
```

**Sync (incremental — only copies changed/new files):**
```bash
azcopy sync \
  "https://<source-storage>.blob.core.windows.net/<container>?<source-SAS>" \
  "https://<target-storage>.blob.core.windows.net/<container>?<target-SAS>" \
  --recursive=true \
  --delete-destination=false
```

> **Security note:** SAS tokens grant direct access. Use minimum permissions, set expiry ≤ 1 hour for production, and rotate after migration. Prefer Entra ID auth where possible.

**Performance tuning:**
```bash
# Set concurrency (default auto-tuned, explicit for large transfers):
azcopy copy <src> <dst> --recursive --cap-mbps 500 --block-size-mb 256
```

### 2.2 Azure Files (SMB File Shares)

**Option 1: AzCopy (recommended for large shares)**
```bash
azcopy copy \
  "https://<source-storage>.file.core.windows.net/<share>?<source-SAS>" \
  "https://<target-storage>.file.core.windows.net/<share>?<target-SAS>" \
  --recursive=true
```

**Option 2: Azure File Sync (for gradual migration with on-premises involvement)**
1. Install Azure File Sync agent on a Windows Server on-premises
2. Register the server with the source storage sync service
3. Sync share to on-premises server
4. Register the same server with the EA sync service
5. Tiered upload to EA storage account

**Option 3: `robocopy` via mounted shares (small shares only)**
```powershell
robocopy \\<source-share-UNC> \\<target-share-UNC> /E /COPYALL /R:3 /W:5 /LOG:robocopy.log
```

### 2.3 Azure SQL Database

**Option 1: Bacpac export/import (recommended for < 200 GB)**

Export from source (CSP):
```bash
az sql db export \
  --resource-group <source-RG> \
  --server <source-server> \
  --name <db-name> \
  --storage-key-type StorageAccessKey \
  --storage-key <storage-key> \
  --storage-uri "https://<storage>.blob.core.windows.net/<container>/<db>.bacpac" \
  --admin-user <admin> \
  --admin-password <password>
```

Import to target (EA):
```bash
az sql db import \
  --resource-group <target-RG> \
  --server <target-server> \
  --name <db-name> \
  --storage-key-type StorageAccessKey \
  --storage-key <target-storage-key> \
  --storage-uri "https://<target-storage>.blob.core.windows.net/<container>/<db>.bacpac" \
  --admin-user <admin> \
  --admin-password <password>
```

**Option 2: Azure Database Migration Service (DMS) — recommended for large or live databases**
- Supports online (minimal downtime) and offline migration
- Source: Azure SQL Database in CSP subscription
- Target: Azure SQL Database in EA subscription
- DMS must have network line-of-sight to both source and target (use VPN from Option B or C above)

```bash
# Create DMS instance in EA subscription:
az dms create \
  --resource-group <RG> \
  --name <dms-name> \
  --location <region> \
  --sku-name Premium_4vCores \
  --virtual-subnet-id <subnet-resource-id>
```

**Option 3: Transactional replication (for near-zero downtime)**
- Configure SQL Server transactional replication from CSP source to EA target
- Replication runs continuously; cutover is a publisher switch
- Requires SQL Server version compatibility between source and target

---

### 2.4 Azure SQL Managed Instance

**Option 1: Native backup/restore to Azure Blob Storage**
```sql
-- On source MI (CSP):
BACKUP DATABASE [<db-name>]
TO URL = 'https://<source-storage>.blob.core.windows.net/<container>/<db>.bak'
WITH CREDENTIAL = '<credential-name>', COMPRESSION, STATS = 10;
```

```sql
-- On target MI (EA):
RESTORE DATABASE [<db-name>]
FROM URL = 'https://<target-storage>.blob.core.windows.net/<container>/<db>.bak'
WITH CREDENTIAL = '<credential-name>', STATS = 10;
```

**Option 2: Managed Instance Link (online migration, minimal downtime)**
- Uses Always On Availability Groups technology
- Replicates MI databases from CSP to EA in near-real-time
- Requires Business Critical or General Purpose tier
- Cut over by failing over the AG

### 2.5 Azure Cosmos DB

**Option 1: Azure Cosmos DB Data Migration Tool (DMT)**
```bash
# Install DMT:
dotnet tool install -g Microsoft.Azure.Cosmos.DataMovementLibrary

# Migrate a container:
dmt migrate \
  --source "AccountEndpoint=<source-endpoint>;AccountKey=<source-key>" \
  --sourceDatabase <source-db> \
  --sourceContainer <source-container> \
  --destination "AccountEndpoint=<target-endpoint>;AccountKey=<target-key>" \
  --destinationDatabase <target-db> \
  --destinationContainer <target-container>
```

**Option 2: Azure Data Factory (ADF) — for large or complex migrations**
- Create ADF in EA subscription
- Source: Cosmos DB linked service pointing to CSP account (using connection string)
- Sink: Cosmos DB linked service pointing to EA account
- Supports parallel copy activity and change feed for incremental loads

**Option 3: Continuous backup + Point-in-time restore (within same tenant only)**
- Not applicable cross-tenant; use DMT or ADF instead

### 2.6 Azure Disk (Managed Disks / VM Data Disks)

Managed Disks cannot be moved across tenants directly. Use one of:

**Option 1: Snapshot → Export → Re-import**
```bash
# Step 1: Create snapshot in CSP:
az snapshot create \
  --resource-group <source-RG> \
  --name <snapshot-name> \
  --source <disk-resource-id>

# Step 2: Generate SAS URL for snapshot (valid for 3600 seconds):
SAS_URL=$(az snapshot grant-access \
  --resource-group <source-RG> \
  --name <snapshot-name> \
  --duration-in-seconds 3600 \
  --query accessSas --output tsv)

# Step 3: Copy VHD to target storage account (EA) using AzCopy:
azcopy copy "$SAS_URL" \
  "https://<target-storage>.blob.core.windows.net/vhds/<disk-name>.vhd?<target-SAS>"

# Step 4: Create managed disk from VHD in EA:
az disk create \
  --resource-group <target-RG> \
  --name <disk-name> \
  --source "https://<target-storage>.blob.core.windows.net/vhds/<disk-name>.vhd" \
  --location <region>
```

**Option 2: Azure Site Recovery (ASR) — for live VM replication with minimal downtime**
- Deploy ASR Recovery Services Vault in EA subscription
- Register CSP VMs with the vault
- Replicate disks to EA subscription
- Perform test failover, then production failover (cutover)
- Supports Windows and Linux VMs

---

### 2.7 Azure Database for PostgreSQL / MySQL

**Option 1: pg_dump / mysqldump + AzCopy**

PostgreSQL:
```bash
# Export from CSP:
pg_dump -h <source-server>.postgres.database.azure.com \
  -U <admin>@<source-server> \
  -d <database> -Fc -f /tmp/backup.dump

# Upload to intermediate blob:
azcopy copy /tmp/backup.dump \
  "https://<storage>.blob.core.windows.net/backups/backup.dump?<SAS>"

# Download to target machine and restore:
pg_restore -h <target-server>.postgres.database.azure.com \
  -U <admin>@<target-server> \
  -d <database> -Fc /tmp/backup.dump
```

MySQL:
```bash
mysqldump -h <source-server>.mysql.database.azure.com \
  -u <admin>@<source-server> -p<password> <database> > /tmp/backup.sql

mysql -h <target-server>.mysql.database.azure.com \
  -u <admin>@<target-server> -p<password> <database> < /tmp/backup.sql
```

**Option 2: Azure Database Migration Service (DMS)**
- Supports online migration for both PostgreSQL and MySQL
- Uses logical replication / binary log replication
- Requires DMS to have network access to both source and target

---

### 2.8 Azure Data Factory (ADF) Pipelines

ADF itself cannot be moved across tenants. Pipelines, datasets, and linked services must be exported and re-imported.

**Export ADF artifacts from CSP:**
```bash
# Export ARM template of entire ADF:
az datafactory export-template \
  --resource-group <source-RG> \
  --factory-name <adf-name>
```

Or use the ADF UI: **Manage → ARM Template → Export ARM template**

**Re-import in EA:**
1. Create a new ADF in the EA subscription
2. Import the ARM template (update linked service connection strings / managed identities)
3. Update all linked services to point to EA target resources
4. Re-create self-hosted integration runtimes if used

## Part 3 — Data Transfer Security Requirements

All data transfers must meet the following security standards:

| Requirement | Implementation |
|---|---|
| Encryption in transit | TLS 1.2+ enforced on all endpoints; AzCopy uses HTTPS by default |
| Encryption at rest | Azure Storage Service Encryption (SSE) enabled on target; customer-managed keys (CMK) where required |
| Authentication | Prefer Entra ID / Managed Identity over SAS keys; rotate SAS tokens immediately after use |
| Network path | Use private endpoints + VPN/ExpressRoute for regulated data; avoid public internet for PII/PHI |
| SAS token hygiene | Minimum permissions, short expiry (≤ 1 hour), revoke after use |
| Audit logging | Enable Storage Analytics / Diagnostic Logs on both source and target accounts during migration |
| Data integrity | Enable MD5 checksum validation: `--check-md5=FailIfDifferent` in AzCopy |
| Access control | Disable public access on storage accounts after migration; remove migration SAS tokens |

## Part 5 — Data Transfer Sequencing & Order

Execute data transfers in this order to respect dependencies:

```
Phase 1 — Network foundation ready (VPN/ER tunnel established)
    │
    ▼
Phase 2 — Secrets & config transferred first
    ├─► Key Vault secrets/keys (export → import to target KV)
    └─► App configuration values (export from App Config → import)
    │
    ▼
Phase 3 — Storage data transfer
    ├─► Blob Storage (AzCopy, largest containers first)
    ├─► ADLS Gen2 (AzCopy with --recursive)
    └─► Azure Files (AzCopy or robocopy)
    │
    ▼
Phase 4 — Database migration
    ├─► Non-production / read replicas first (validate process)
    ├─► Azure SQL / MI (DMS online migration — start replication)
    ├─► PostgreSQL / MySQL (DMS or dump/restore)
    └─► Cosmos DB (DMT or ADF pipeline)
    │
    ▼
Phase 5 — VM disk migration
    ├─► Non-production VMs first
    └─► Production VMs (ASR with test failover → production failover)
    │
    ▼
Phase 6 — Final sync & validation
    ├─► Re-run AzCopy sync for any changed blobs since initial copy
    ├─► Validate row counts / checksums on all databases
    └─► Validate application connectivity end-to-end
    │
    ▼
Phase 7 — Cutover
    ├─► DNS update (new public IPs / FQDNs)
    ├─► DMS cutover (complete replication)
    └─► Disable write access on CSP source resources
```

## Part 6 — Cost Estimation for Data Transfer

| Transfer Method | Egress Cost (approx.) | Speed | Best For |
|---|---|---|---|
| Internet (public endpoint) | ~$0.05–$0.08/GB | Up to ~Gbps | < 1 TB, non-sensitive |
| S2S VPN | ~$0.05–$0.08/GB + VPN GW hr | 0.65–1.25 Gbps | 1–10 TB, private |
| ExpressRoute (metered) | ~$0.025–$0.05/GB | 1–10 Gbps | > 10 TB, regulated |
| ExpressRoute (unlimited) | Fixed monthly fee | 1–10 Gbps | Continuous/large volumes |
| Data Box (offline) | Shipping + device fee | N/A (physical) | > 40 TB one-time |
| AzCopy (same-region) | Free (intra-region) | Very high | Source/target in same region |

> **Tip:** If the CSP and EA resources are in the **same Azure region**, transfer within that region is free of egress charges when using service-to-service copy (e.g., AzCopy with service URLs). Route your transfer through the same region to eliminate egress costs.

## Part 7 — Validation Checklist After Data Transfer

| Item | Validation Method | Status |
|---|---|---|
| Blob data integrity | `azcopy jobs show <id>` — check Bytes Transferred vs. source size | ☐ |
| MD5 checksum match | `--check-md5=FailIfDifferent` in AzCopy — zero failures | ☐ |
| SQL row counts | `SELECT COUNT(*) FROM <table>` — match source and target | ☐ |
| SQL schema validation | Compare `INFORMATION_SCHEMA.TABLES` / `COLUMNS` | ☐ |
| Cosmos DB document count | Compare container item count (source vs. target) | ☐ |
| File share content | `azcopy list` on target vs. source — file counts match | ☐ |
| VM disk boot | Start migrated VM — OS boots successfully | ☐ |
| Application connectivity | App can connect to target databases and storage | ☐ |
| Private endpoint DNS | `Resolve-DnsName` returns private IP for all service FQDNs | ☐ |
| No data remaining in CSP | Confirm source resources are empty before decommission | ☐ |

## Part 8 — Useful Reference Commands

```bash
# List all storage accounts in CSP subscription:
az storage account list --output table --query "[].{Name:name, RG:resourceGroup, Location:location}"

# Get storage account size (approximate via metrics):
az monitor metrics list \
  --resource <storage-account-resource-id> \
  --metric BlobCapacity \
  --interval PT1H \
  --output table

# List AzCopy active jobs:
azcopy jobs list

# Check AzCopy job summary:
azcopy jobs show <job-id> --with-status=Failed

# Verify DMS migration activity:
az dms project task list --resource-group <RG> --service-name <dms> --project-name <project>

# Check SQL DB export status:
az sql db op list --resource-group <RG> --server <server> --database <db> --output table

# Check ASR replication health:
az site-recovery replication-protected-item list \
  --resource-group <RG> \
  --vault-name <vault-name> \
  --fabric-name <fabric> \
  --protection-container-name <container>
```
