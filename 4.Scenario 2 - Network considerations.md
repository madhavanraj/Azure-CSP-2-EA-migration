# Scenario 2 — Network Considerations: CSP Tenant → EA Tenant (Different Tenants)

This document covers the network-specific considerations when migrating Azure resources from a CSP tenant to an EA tenant where the two tenants are **different**. Because no direct ARM move or Azure Migrate is supported across tenants, all network resources must be **recreated** in the target tenant. Careful planning is essential to avoid connectivity gaps and downtime.

---

## Key Principle

> **Virtual Networks (VNets), subnets, NSGs, route tables, and all associated networking resources are tenant-scoped and cannot be moved across tenants. They must be fully recreated in the target EA tenant.**

---

## Network Architecture Migration — Step-by-Step

The migration is organized into **5 phases**: Discovery → Design → Build → Cutover → Validate. Each phase must be completed in order. Do **not** decommission source networking until Phase 5 validation passes.

---

### Phase 1 — Discovery & Inventory (Source Tenant)

> Goal: Produce a complete, exportable inventory of every network resource in the CSP subscription before touching anything.

**Step 1 — Export all VNets and subnets**
```bash
az network vnet list --output table
az network vnet list --query "[].{Name:name, RG:resourceGroup, AddressSpace:addressSpace.addressPrefixes}" --output table
# For each VNet, export subnets:
az network vnet subnet list --vnet-name <VNetName> --resource-group <RG> --output table
```

**Step 2 — Export NSGs and all rules**
```bash
az network nsg list --output table
# For each NSG, export rules:
az network nsg rule list --nsg-name <NSGName> --resource-group <RG> --output table
```

**Step 3 — Export Route Tables (UDRs)**
```bash
az network route-table list --output table
az network route-table show --name <RTName> --resource-group <RG> --query "routes" --output table
```

**Step 4 — Export VPN Gateway configuration (if applicable)**
```bash
az network vnet-gateway show --name <GWName> --resource-group <RG>
az network vpn-connection list --resource-group <RG> --output table
az network local-gateway list --resource-group <RG> --output table
```

**Step 5 — Export Azure Firewall Policy and rules**
```bash
az network firewall list --output table
az network firewall policy list --output table
```

**Step 6 — Export Application Gateway / WAF configuration**
```bash
az network application-gateway list --output table
az network application-gateway show --name <AGName> --resource-group <RG>
```

**Step 7 — Export Load Balancer configurations**
```bash
az network lb list --output table
az network lb show --name <LBName> --resource-group <RG>
```

**Step 8 — Export Private Endpoints and DNS Zones**
```bash
az network private-endpoint list --output table
az network private-dns zone list --output table
# For each private DNS zone, export records:
az network private-dns record-set list --zone-name <ZoneName> --resource-group <RG> --output table
```

**Step 9 — Export Public DNS Zones (if hosted in Azure DNS)**
```bash
az network dns zone list --output table
az network dns record-set list --zone-name <ZoneName> --resource-group <RG> --output table
```

**Step 10 — Bulk inventory via Azure Resource Graph**
```bash
az graph query -q "Resources | where type startswith 'microsoft.network' | project name, type, resourceGroup, location | order by type asc" --output table
```

**Step 11 — Document public IP addresses in use**
```bash
az network public-ip list --output table --query "[].{Name:name, IP:ipAddress, SKU:sku.name, Allocation:publicIPAllocationMethod}"
```

> **Deliverable:** A spreadsheet / IaC parameter file mapping every network resource: name, resource group, region, CIDR, rules, SKU, and all dependencies.

### Phase 2 — Network Architecture Design (Target Tenant)

> Goal: Design the target EA tenant network topology before deploying any resources. Resolve conflicts proactively.

**Step 1 — Validate CIDR availability in the EA tenant**
- Run the Resource Graph query from Phase 1, Step 10 against the EA tenant.
- Confirm that the same address spaces from the CSP tenant are available (no overlapping VNets or on-premises ranges).
- If conflicts exist, assign new CIDR ranges and update the IP address plan accordingly.

**Step 2 — Design the target topology**
Choose the pattern that matches your CSP architecture:

| Source Pattern | Target Pattern | Notes |
|---|---|---|
| Single VNet | Single VNet | Direct 1:1 recreation |
| Hub-and-Spoke | Hub-and-Spoke | Recreate hub first, then spokes; re-establish VNet peerings |
| Mesh / peered VNets | Mesh / peered VNets | Document all peering pairs before migration |
| VNet with on-prem VPN | VNet with VPN Gateway | New gateway IPs; update on-prem firewall/VPN device |
| VNet with ExpressRoute | VNet with ExpressRoute | Re-authorize circuit in EA tenant |

**Step 3 — Plan subnet layout and delegation order**

Provision subnets in this order to avoid dependency failures:

1. `GatewaySubnet` (if VPN/ExpressRoute gateway needed) — minimum `/27`
2. `AzureFirewallSubnet` (if Azure Firewall needed) — minimum `/26`
3. `AzureFirewallManagementSubnet` (if forced tunneling) — minimum `/26`
4. `AzureBastionSubnet` (if Bastion needed) — minimum `/26`
5. Application / workload subnets
6. Database / private endpoint subnets

**Step 4 — Identify new public IP addresses**
- All Standard SKU public IPs will be **new** in the EA tenant.
- Compile a list of all DNS A/CNAME records, external firewall ACLs, and third-party allowlists that reference the current public IPs.
- Plan DNS and allowlist updates as part of the cutover window.

**Step 5 — Plan DNS strategy**
- Decide if Azure DNS Public Zones will be re-hosted in the EA subscription.
- Plan for NS record delegation cutover at the domain registrar.
- Design the Private DNS zone naming and VNet-link strategy for the EA tenant.

**Step 6 — Produce IaC templates**
- Author Bicep or Terraform modules for every network resource based on the Phase 1 inventory.
- Parameterize environment-specific values (names, CIDR ranges, SKUs).
- Store templates in source control.

### Phase 3 — Build Network Infrastructure (Target Tenant)

> Goal: Deploy all network infrastructure in the EA tenant **before** migrating any workloads. Follow the dependency order below.

**Dependency Build Order (must be followed strictly):**

```
1. Resource Groups
2. VNets + Subnets (including reserved subnets for Gateway, Firewall, Bastion)
3. Application Security Groups (ASGs)
4. Network Security Groups (NSGs) + rules
5. Route Tables (UDRs) — associate to subnets AFTER Firewall is deployed
6. Azure Firewall (requires AzureFirewallSubnet)
7. UDR associations (now that Firewall private IP is known)
8. VPN Gateway OR ExpressRoute Gateway (30–45 min provisioning)
9. Local Network Gateways + VPN Connections
10. Azure Bastion
11. Load Balancers (internal first, then external)
12. Application Gateway / WAF
13. Private DNS Zones + VNet links
14. (Workload resources deployed next — VMs, PaaS services)
15. Private Endpoints (after workload resources exist)
16. Public DNS Zone records (after public IPs are known)
```

**Step 1 — Create Resource Groups**
```bash
az group create --name <RGName> --location <Region>
```

**Step 2 — Deploy VNets and subnets**
```bash
az network vnet create \
  --name <VNetName> \
  --resource-group <RGName> \
  --address-prefixes <CIDR> \
  --location <Region>

az network vnet subnet create \
  --name <SubnetName> \
  --vnet-name <VNetName> \
  --resource-group <RGName> \
  --address-prefix <SubnetCIDR>
```

**Step 3 — Deploy NSGs and associate to subnets**
```bash
az network nsg create --name <NSGName> --resource-group <RGName>
az network nsg rule create --nsg-name <NSGName> --resource-group <RGName> \
  --name <RuleName> --priority <Priority> \
  --access Allow --protocol Tcp \
  --source-address-prefixes <Source> --source-port-ranges '*' \
  --destination-address-prefixes <Dest> --destination-port-ranges <Port> \
  --direction Inbound

# Associate NSG to subnet:
az network vnet subnet update \
  --name <SubnetName> --vnet-name <VNetName> --resource-group <RGName> \
  --network-security-group <NSGName>
```

**Step 4 — Deploy Route Tables (without UDR for firewall yet)**
```bash
az network route-table create --name <RTName> --resource-group <RGName>
# Add routes after Firewall is deployed (Step 6)
```

**Step 5 — Deploy Azure Firewall (if applicable)**
```bash
# Deploy Firewall Policy first:
az network firewall policy create --name <PolicyName> --resource-group <RGName>

# Deploy Firewall:
az network firewall create \
  --name <FWName> --resource-group <RGName> \
  --sku AZFW_VNet --tier Standard \
  --vnet-name <VNetName> \
  --firewall-policy <PolicyName>
```

**Step 6 — Add UDR pointing to Firewall private IP**
```bash
# Get Firewall private IP:
FW_IP=$(az network firewall show --name <FWName> --resource-group <RGName> \
  --query "ipConfigurations[0].privateIPAddress" --output tsv)

az network route-table route create \
  --route-table-name <RTName> --resource-group <RGName> \
  --name route-to-firewall \
  --address-prefix 0.0.0.0/0 \
  --next-hop-type VirtualAppliance \
  --next-hop-ip-address $FW_IP

# Associate route table to subnet:
az network vnet subnet update \
  --name <SubnetName> --vnet-name <VNetName> --resource-group <RGName> \
  --route-table <RTName>
```

**Step 7 — Deploy VPN Gateway (if applicable)**
```bash
# Provision GatewaySubnet first (already done in Step 2)
az network vnet-gateway create \
  --name <GWName> --resource-group <RGName> \
  --vnet <VNetName> \
  --gateway-type Vpn --vpn-type RouteBased \
  --sku VpnGw2AZ --generation Generation2 \
  --public-ip-address <PIPName> \
  --no-wait   # ~30-45 minutes
```

**Step 8 — Deploy Local Network Gateways and Connections**
```bash
az network local-gateway create \
  --name <LNGName> --resource-group <RGName> \
  --gateway-ip-address <OnPremPublicIP> \
  --local-address-prefixes <OnPremCIDR>

az network vpn-connection create \
  --name <ConnName> --resource-group <RGName> \
  --vnet-gateway1 <GWName> \
  --local-gateway2 <LNGName> \
  --shared-key <PreSharedKey>
```

**Step 9 — Deploy Azure Bastion (if applicable)**
```bash
az network bastion create \
  --name <BastionName> --resource-group <RGName> \
  --vnet-name <VNetName> \
  --public-ip-address <BastionPIPName> \
  --sku Standard
```

**Step 10 — Deploy Load Balancers**
```bash
# Internal Load Balancer example:
az network lb create \
  --name <ILBName> --resource-group <RGName> \
  --sku Standard --vnet-name <VNetName> \
  --subnet <SubnetName> --private-ip-address <PrivateIP> \
  --frontend-ip-name <FEName> --backend-pool-name <BEPool>
```

**Step 11 — Deploy Application Gateway / WAF**
```bash
az network application-gateway create \
  --name <AGName> --resource-group <RGName> \
  --vnet-name <VNetName> --subnet <AGSubnetName> \
  --sku WAF_v2 --capacity 2 \
  --public-ip-address <AGPIPName> \
  --http-settings-port 80 --http-settings-protocol Http \
  --frontend-port 443 --routing-rule-type Basic
```

**Step 12 — Deploy Private DNS Zones and VNet links**
```bash
az network private-dns zone create \
  --name "privatelink.blob.core.windows.net" \
  --resource-group <RGName>

az network private-dns link vnet create \
  --name <LinkName> \
  --resource-group <RGName> \
  --zone-name "privatelink.blob.core.windows.net" \
  --virtual-network <VNetName> \
  --registration-enabled false
```

**Step 13 — Validate pre-workload network connectivity**
```bash
# Check VPN tunnel status:
az network vpn-connection show --name <ConnName> --resource-group <RGName> \
  --query "connectionStatus"

# Check Firewall provisioning:
az network firewall show --name <FWName> --resource-group <RGName> \
  --query "provisioningState"

# Check Gateway provisioning:
az network vnet-gateway show --name <GWName> --resource-group <RGName> \
  --query "provisioningState"
```

### Phase 4 — Workload Migration & Private Endpoint Recreation

> Goal: After network foundation is in place, migrate workloads and attach them to the new network.

**Step 1 — Migrate VMs / PaaS services** (via Azure Site Recovery, backup-restore, or IaC redeploy)

**Step 2 — Recreate Private Endpoints**
```bash
# After target service (e.g., storage account) is deployed:
az network private-endpoint create \
  --name <PEName> --resource-group <RGName> \
  --vnet-name <VNetName> --subnet <SubnetName> \
  --private-connection-resource-id <TargetResourceID> \
  --group-id blob \
  --connection-name <ConnName>
```

**Step 3 — Add Private DNS A records**
```bash
# Get the private endpoint NIC IP:
PE_IP=$(az network private-endpoint show --name <PEName> --resource-group <RGName> \
  --query "customDnsConfigs[0].ipAddresses[0]" --output tsv)

az network private-dns record-set a add-record \
  --resource-group <RGName> \
  --zone-name "privatelink.blob.core.windows.net" \
  --record-set-name <StorageAccountName> \
  --ipv4-address $PE_IP
```

**Step 4 — Update application connection strings and DNS references**
- Update all app config / Key Vault secrets that reference old resource FQDNs or private IPs.
- Validate DNS resolution from within the EA VNet:
```powershell
Resolve-DnsName <storageaccount>.blob.core.windows.net
# Should return a 10.x.x.x private IP, not the public Azure IP
```

---

### Phase 5 — Cutover & Validation

> Goal: Switch traffic to the EA tenant network and confirm all connectivity is healthy before decommissioning the CSP tenant network.

**Step 1 — Update external DNS records**
- Update A/CNAME records at the domain registrar or Azure DNS for all public-facing endpoints (Load Balancers, Application Gateways) to point to the new public IPs.
- Set low TTL (60–300 seconds) 24–48 hours before cutover to speed propagation.

**Step 2 — Update external firewall ACLs and third-party allowlists**
- Replace old CSP public IPs with new EA public IPs in all external firewall rules.
- Notify third-party vendors/partners of IP changes.

**Step 3 — Update on-premises VPN device (if S2S VPN)**
- Update the peer IP on the on-premises VPN device to the new Azure VPN Gateway public IP.
- If BGP, verify that the new ASN / BGP peer IP is configured.

**Step 4 — Run end-to-end connectivity validation**

| Test | Command | Expected Result |
|---|---|---|
| VNet-to-VNet peering | `Test-NetConnection <PeerVMIP> -Port 22` | TCP Connected |
| Private Endpoint DNS | `Resolve-DnsName <resource>.privatelink.blob.core.windows.net` | Private IP returned |
| VPN Tunnel | `az network vpn-connection show --query connectionStatus` | `Connected` |
| NSG effective rules | `az network nic show-effective-nsg --name <NIC> --resource-group <RG>` | Rules match expected |
| App Gateway health | `az network application-gateway show-backend-health --name <AGName> --resource-group <RG>` | Backends `Healthy` |
| Bastion connectivity | Connect to a VM via Azure Bastion in the portal | Session established |
| Internet egress (via Firewall) | `curl -s https://ifconfig.me` from a VM | Returns Firewall public IP |

**Step 5 — Run Azure Network Watcher validation**
```bash
# IP flow verify (test NSG allow/deny):
az network watcher test-ip-flow \
  --resource-group <RG> --vm <VMName> \
  --direction Inbound --protocol TCP \
  --local <VMIP>:<Port> --remote <SourceIP>:*

# Next hop check:
az network watcher show-next-hop \
  --resource-group <RG> --vm <VMName> \
  --source-ip <VMIP> --dest-ip <DestIP>
```

**Step 6 — Decommission CSP tenant network resources** *(only after all validations pass)*
- Remove Private Endpoints, Gateways, Firewalls, and VNets from the CSP tenant.
- Cancel any reserved public IPs in the CSP subscription.
- Archive all IaC templates and documentation.

## 1. Virtual Networks (VNets) and Subnets

### What Cannot Be Transferred
- VNets are subscription-scoped resources and do not survive a cross-tenant move.
- Subnet configurations, CIDR blocks, delegations, and service endpoint policies must be recreated manually or via IaC.

### Considerations
- **Address Space Conflicts:** Audit the existing VNet address spaces in the CSP tenant and validate there are no CIDR conflicts with existing networks in the target EA tenant (especially in hub-and-spoke or shared-services architectures).
- **Subnet Delegation:** Document any subnet delegations (e.g., to Azure App Service, Azure Bastion, Azure Firewall, Azure SQL Managed Instance) and recreate them in the target.
- **Service Endpoints:** Re-enable any VNet service endpoints (e.g., `Microsoft.Storage`, `Microsoft.Sql`, `Microsoft.KeyVault`) on the target subnets and update the corresponding resource firewall rules.

### Recommended Actions
| Action | Notes |
|---|---|
| Export all VNet and subnet configurations | Use `az network vnet list` and `az network vnet subnet list` |
| Document all CIDR ranges in use | Avoid IP overlap in the target tenant |
| Recreate VNets and subnets in target tenant via Bicep/Terraform | Ensures repeatability and consistency |
| Re-enable service endpoints per subnet | Match source configuration exactly |

---

## 2. Network Security Groups (NSGs)

### What Cannot Be Transferred
- NSG objects and their associated rules are subscription-bound and must be recreated.
- NSG flow logs tied to Azure Monitor / Log Analytics workspaces in the source tenant will be lost.

### Considerations
- **Rule Inventory:** Export all inbound and outbound security rules including priorities, protocols, source/destination IP ranges, and port ranges.
- **Application Security Groups (ASGs):** If ASGs are used within NSG rules, these must also be recreated before the NSG rules that reference them.
- **Association Mapping:** Document which NSGs are associated with which subnets and NICs.
- **NSG Flow Logs:** Reconfigure flow logs to point to a new Log Analytics workspace in the target tenant.

### Recommended Actions
| Action | Notes |
|---|---|
| Export NSG rules | `az network nsg rule list --nsg-name <name>` |
| Recreate ASGs first, then NSGs | ASG references in rules require ASGs to exist |
| Re-associate NSGs to subnets and NICs | Verify post-migration using Network Watcher |
| Reconfigure NSG flow logs | Point to new Log Analytics workspace in EA tenant |

---

## 3. Route Tables (User-Defined Routes)

### Considerations
- Custom route tables (UDRs) used for forced tunnelling, NVA traffic inspection, or spoke-to-hub routing must be recreated.
- Validate that next-hop IP addresses (e.g., Azure Firewall private IP, NVA IPs) are consistent between source and target environments.
- Default BGP route propagation settings must be re-applied.

### Recommended Actions
| Action | Notes |
|---|---|
| Document all UDRs and associated subnets | `az network route-table list` |
| Confirm next-hop IPs are valid in the target VNet | NVA or firewall IPs may differ |
| Recreate route tables and re-associate to subnets | Re-enable or disable BGP propagation as needed |

---

## 4. VPN Gateways

### What Cannot Be Transferred
- VPN Gateways are VNet-attached resources and cannot be moved across tenants. They must be deleted from the source and recreated in the target.

### Considerations
- **SKU and Generation:** Document the Gateway SKU (e.g., VpnGw1, VpnGw2AZ) and generation (Generation1/Generation2) to ensure the correct SKU is provisioned in the target.
- **BGP Configuration:** If BGP is enabled, document the ASN and BGP peer IP address.
- **Local Network Gateways:** Document all Local Network Gateway configurations (on-premises IP, address prefixes) for Site-to-Site (S2S) connections.
- **Shared Keys:** Retrieve and securely store pre-shared keys for all S2S connections before decommissioning the source gateway.
- **Gateway Subnet:** Ensure the `/27` or larger `GatewaySubnet` is reserved in the target VNet before deploying the gateway.
- **Downtime Window:** VPN Gateway provisioning takes 30–45 minutes. Plan a maintenance window that accommodates this.

### Recommended Actions
| Action | Notes |
|---|---|
| Document gateway SKU, generation, BGP settings | `az network vnet-gateway show` |
| Document all connections and Local Network Gateways | Include shared keys (store securely in Key Vault) |
| Provision GatewaySubnet in target VNet | Minimum `/27` prefix |
| Deploy new VPN Gateway in target tenant | Allow 30–45 min provisioning time |
| Recreate connections and validate tunnel status | `az network vpn-connection show` |

---

## 5. ExpressRoute Circuits

### What Cannot Be Transferred
- ExpressRoute circuits are billing-scoped and tied to the CSP subscription. When migrating to a different EA tenant, the circuit authorization and gateway connection must be re-established.

### Considerations
- **Circuit Ownership:** Determine whether the ExpressRoute circuit is owned by the customer or the CSP partner. CSP-owned circuits cannot be reused directly.
- **Authorization Keys:** If the circuit is customer-owned, generate a new authorization key and connect it to the new Virtual Network Gateway in the EA tenant.
- **Peering Configurations:** Document all peering types (Private Peering, Microsoft Peering), ASNs, VLAN IDs, and peer IPs.
- **Redundancy:** Validate that the target gateway is zone-redundant (ErGw1AZ or higher) if the source used zone redundancy.
- **Downtime:** Cutover from source to target circuit connection will cause a connectivity interruption. Coordinate with the connectivity provider.

### Recommended Actions
| Action | Notes |
|---|---|
| Confirm circuit ownership (customer vs. CSP) | Determines if reuse is possible |
| Document all peering configurations | Private and Microsoft Peering details |
| Generate new authorization keys for customer-owned circuits | Provide to EA tenant administrators |
| Recreate ExpressRoute Gateway and connection in target VNet | Match SKU and zone redundancy |
| Test private connectivity before cutover | Validate BGP routes are received |

---

## 6. Azure Firewall

### What Cannot Be Transferred
- Azure Firewall instances are VNet-attached and must be recreated in the target tenant.

### Considerations
- **Policy vs. Classic Rules:** Determine whether the source uses Azure Firewall Policy (recommended) or classic rules. Export the policy and all rule collections.
- **Firewall SKU:** Document whether Standard or Premium SKU is used. Premium enables TLS inspection and IDPS.
- **Public IP Addresses:** Azure Firewall public IPs cannot be transferred across tenants. New public IPs will be assigned. Update any external firewall rules or DNS records accordingly.
- **Forced Tunneling:** If forced tunneling is enabled, ensure the management subnet (`AzureFirewallManagementSubnet`) is recreated in the target VNet.
- **DNAT / SNAT Rules:** Document all DNAT and SNAT rules for re-creation.

### Recommended Actions
| Action | Notes |
|---|---|
| Export Azure Firewall Policy and all rule collections | `az network firewall policy export` or portal |
| Note Firewall SKU and forced tunneling config | |
| Recreate `AzureFirewallSubnet` and `AzureFirewallManagementSubnet` | Minimum `/26` for each |
| Deploy new Firewall in target tenant with same policy | Update UDRs to point to new firewall private IP |
| Update DNS records and external ACLs with new public IPs | Coordinate with DNS and security teams |

---

## 7. Load Balancers

### What Cannot Be Transferred
- Azure Load Balancers (Standard or Basic) cannot be moved across tenants.

### Considerations
- **Public vs. Internal:** Document whether each LB is public-facing or internal (ILB).
- **Frontend IP Configurations:** Public frontend IPs cannot be transferred. Internal frontend IPs (from VNet address space) can be recreated with the same private IP if the VNet address space is identical.
- **Backend Pools, Health Probes, and Rules:** Export all load balancing rules, NAT rules, health probe configurations, and backend pool members.
- **Standard vs. Basic SKU:** Basic SKU load balancers should be migrated to Standard SKU in the target tenant per Microsoft best practices.

### Recommended Actions
| Action | Notes |
|---|---|
| Document all LB frontend configs, backend pools, rules, and probes | `az network lb show` |
| Recreate LBs in target tenant (use Standard SKU) | |
| Re-associate backend pool members (VMs/NICs) post-VM migration | |
| Update DNS records for public LB frontend IPs | New public IPs will be assigned |

---

## 8. Application Gateway / WAF

### What Cannot Be Transferred
- Application Gateways are subnet-attached and must be recreated in the target tenant.

### Considerations
- **SKU Tier:** Document WAF v1 vs. WAF v2 (v2 is strongly recommended). Do not recreate v1 in the target tenant; use this migration as an opportunity to upgrade to v2.
- **SSL/TLS Certificates:** Export all SSL certificates (listener and backend authentication certificates) before migration. Store them securely in Azure Key Vault.
- **WAF Policy:** Export custom WAF rules, managed rule sets, and exclusions. Recreate as a WAF Policy resource in the target tenant.
- **Backend Pools and Routing Rules:** Document all HTTP settings, backend pools, routing rules, and URL path maps.
- **Public IP:** A new public IP will be assigned. Update DNS A/CNAME records accordingly.

### Recommended Actions
| Action | Notes |
|---|---|
| Export SSL certificates to Key Vault | Recreate Key Vault in target tenant first |
| Document WAF policy, custom rules, and exclusions | |
| Recreate Application Gateway (v2 SKU recommended) | |
| Re-import certificates and reconfigure backend pools | |
| Update DNS records with new public IP | |

---

## 9. Private Endpoints and Private DNS Zones

### What Cannot Be Transferred
- Private Endpoints are NIC-backed resources tied to the VNet and cannot be moved across tenants.
- Private DNS Zones can be exported and recreated but DNS links to VNets must be reestablished.

### Considerations
- **Service Coverage:** Inventory all private endpoints across all services (Storage, Key Vault, SQL, CosmosDB, Service Bus, Event Hubs, etc.).
- **Private DNS Zone Records:** Export all A records from private DNS zones (e.g., `privatelink.blob.core.windows.net`).
- **VNet Links:** After recreating private DNS zones in the target tenant, re-link them to the target VNets.
- **DNS Resolution Chain:** If using a custom DNS forwarder (e.g., Azure DNS Private Resolver or a custom DNS VM), ensure it is recreated and configured to forward `*.privatelink.*` queries to `168.63.129.16`.

### Recommended Actions
| Action | Notes |
|---|---|
| Inventory all private endpoints by service type | `az network private-endpoint list` |
| Export DNS zone records | `az network private-dns record-set list` |
| Recreate private DNS zones and VNet links in target tenant | |
| Recreate private endpoints after target services are deployed | |
| Validate DNS resolution end-to-end | Use `nslookup` or `Resolve-DnsName` from within the VNet |

---

## 10. Azure Bastion

### What Cannot Be Transferred
- Azure Bastion is a VNet-deployed PaaS service and must be recreated in the target tenant.

### Considerations
- **Subnet:** Reserve `AzureBastionSubnet` (minimum `/26`) in the target VNet.
- **SKU:** Document whether Basic or Standard SKU is in use. Standard enables tunneling, IP-based connections, and file transfer.
- **Public IP:** A new public IP will be assigned. No DNS update is typically required as Bastion is accessed via the Azure portal.

---

## 11. DNS Considerations

### Azure DNS Zones
- Azure DNS Public Zones with the same zone name may already be claimed in the target tenant. Validate availability before migration.
- Export all DNS record sets using `az network dns record-set list` and reimport to the target tenant.
- Re-delegate name servers at the registrar after the new zone is created (new NS records will be assigned).

### Private DNS Zones
- See Section 9. Private DNS zones for `*.privatelink.*` namespaces must be recreated and re-linked.

### Custom DNS Servers
- If VNets are configured to use custom DNS server IPs, ensure those servers are reachable from the target VNet after migration.
- Update the VNet DNS server settings in the target environment post-recreation.

---

## 12. Network Watcher

### Considerations
- Azure Network Watcher is automatically enabled per region per subscription. It will be present in the target EA subscription.
- **Flow Logs:** NSG flow logs and VNet flow logs must be reconfigured to point to a storage account and optionally a Log Analytics workspace in the target tenant.
- **Connection Monitor:** Recreate any Connection Monitor tests to validate end-to-end connectivity after migration.
- **Traffic Analytics:** Re-enable Traffic Analytics if it was configured in the source, linking to the new workspace.

---

## 13. IP Address Management (IPAM)

### Considerations
- Maintain an IP address plan that maps existing CSP VNet/subnet CIDR blocks to the corresponding target EA VNets.
- If the target EA tenant already has existing VNets, audit for CIDR overlaps **before** migration begins.
- Public IP addresses (Standard SKU) cannot be transferred across tenants. New IPs will be issued — update all external DNS records, firewall rules, and third-party allowlists accordingly.
- Static private IPs assigned to NICs or internal load balancer frontends can be preserved if the address space is replicated exactly in the target VNet.

---

## 14. Hybrid Connectivity Checklist

For workloads with on-premises connectivity (S2S VPN or ExpressRoute):

| Item | Action |
|---|---|
| VPN or ExpressRoute gateway in target VNet | Recreate and validate tunnel establishment |
| On-premises firewall rules | Update to allow traffic from new Azure public IPs / tunnel endpoints |
| BGP route advertisements | Validate that on-premises routes are received in target VNet |
| DNS forwarding from on-premises | Ensure on-premises DNS forwards Azure Private DNS queries correctly |
| Forced tunnelling UDRs | Recreate and re-associate to subnets |
| Network Performance Monitor / Connection Monitor | Reconfigure for new connectivity paths |

## 15. Summary: Network Resources That Must Be Recreated

| Resource | Transferable | Action Required |
|---|---|---|
| Virtual Networks & Subnets | ❌ No | Recreate via IaC; validate CIDR ranges |
| Network Security Groups | ❌ No | Export rules; recreate and re-associate |
| Route Tables (UDRs) | ❌ No | Export; recreate and re-associate |
| VPN Gateway | ❌ No | Recreate; plan downtime window |
| ExpressRoute Connection | ❌ No | Re-authorize circuit; recreate gateway connection |
| Azure Firewall | ❌ No | Export policy; recreate; update UDRs |
| Load Balancer | ❌ No | Export config; recreate (upgrade to Standard) |
| Application Gateway / WAF | ❌ No | Export certs and policy; recreate |
| Private Endpoints | ❌ No | Recreate after target services are deployed |
| Private DNS Zones | ❌ No | Export records; recreate and re-link to VNet |
| Public IP Addresses | ❌ No | New IPs issued; update DNS and allowlists |
| Azure Bastion | ❌ No | Recreate in target VNet |
| NSG Flow Logs | ❌ No | Reconfigure to new storage/workspace |
| Azure DNS Public Zones | ❌ No | Export records; re-create; update NS at registrar |
